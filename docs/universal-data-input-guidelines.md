# Nine record types feed the placement algorithm

The algorithm needs **nine kinds of input record**, and they fall into three groups. The first group describes the chip and how it was stressed: chip identity, total-dose tests, single-event tests, and thermal or electrical wear tests. The second describes where the chip goes: the vehicle's trajectory, the radiation environment along it, and the chip's placement inside the vehicle. The third holds back what really happened, so the algorithm can be checked: observed outcomes on the ground and in orbit, plus a provenance block attached to every value. The single most important finding is about the mechanism. **xAI's API offers retrieval (Collections and the `file_search` tool) but no fine-tuning endpoint** ([xAI API reference](https://api.x.ai/docs/); [Collections search tool](https://docs.x.ai/developers/tools/collections-search)). "Training through xAI RAG" therefore means Grok reads these records at query time and proposes changes to a deterministic algorithm. Grok's weights never change. That makes the outcome records just as important as the inputs: without held-out observed failures, nothing can tell a better algorithm from a more confident one. The guidelines below are built from published test standards (ESCC 25100, ESCC 22900, MIL-STD-883 TM 1019, JEDEC JEP122) and model input contracts (CREME96, IRENE AE9/AP9, CCSDS orbit messages). Any lab's data that fills the required fields can be used. The NVIDIA demo can be filled from public Jetson Orin beam tests and Meta's H100 field data. One gap remains: I found no public beam test data and no public on-orbit telemetry for a data-center NVIDIA GPU.

## RAG retrieves evidence; a scored loop does the learning

Collections stores files, builds an embedding index, and serves hybrid keyword-and-semantic search. Grok calls it through `file_search` in the Responses API, or through `collections_search` in the xAI SDK ([Collections search tool](https://docs.x.ai/developers/tools/collections-search)). The data **is not used for model training** ([xAI Collections](https://docs.x.ai/docs/guides/using-collections)). The workable loop has three steps. Grok retrieves test and environment records. It then writes or tweaks the scoring code or parameters (for example a Weibull fit, a shielding weight, or an Arrhenius activation energy). Finally, a separate evaluator runs the revised algorithm against outcome records Grok did not see, and keeps the change only if the error drops. Grok's job is to propose and the evaluator's job is to decide. This matches the existing 3rok principle "AI proposes, physics disposes" in `docs/PHASE-PLAN.md`.

The platform puts five hard constraints on the data. **Files max out at 100 MB.** CSV, JSON, PDF, XLSX and Markdown are all ingested ([xAI Collections](https://docs.x.ai/docs/guides/using-collections)). Each collection declares typed metadata fields up front, and each field can be marked `required`, `unique`, or `inject_into_chunk`. That last option prepends the field's value to every chunk, so a fragment of a table still knows which chip it describes ([xAI metadata fields](https://docs.x.ai/developers/files/collections/metadata)). Search filters use AIP-160 syntax (`=`, `!=`, `<`, `>=`, `AND`, `OR`, ranges like `field:10..20`). String matching is exact, with no wildcards, and **filtering on a field a document lacks returns nothing** ([xAI collections search API](https://docs.x.ai/developers/rest-api-reference/collections/search)). In practice this means three things. Every structured record must carry the same controlled field names. Numbers belong in CSV or JSON, not locked inside PDF tables. And the source PDF is uploaded alongside, sharing a `record_id`, so Grok can cite the page.

| Metadata field (collection-level) | Flags | Why |
|---|---|---|
| `record_id` | required, unique | Joins a structured row to its source PDF and to its outcome records |
| `record_type` | required, inject | One of the nine types below; drives filtering |
| `chip_family`, `part_number` | required, inject | Lets one chip's records be pulled without the others bleeding in |
| `test_or_model` | required | e.g. `ESCC25100`, `TM1019`, `AE9AP9`, `CCSDS-OEM`, `field-log` |
| `particle_or_stress` | optional | `proton`, `heavy-ion`, `Co-60`, `thermal-cycle`, … |
| `split` | required | `train` or `holdout`; the evaluator only reads `holdout` |
| `source_url`, `value_status` | required | Provenance, and measured vs derived vs assumed (see the last section) |

## Chip-side records follow the test standards, not a new schema

There's no need to invent fields. European and US radiation test standards already say what a test report must contain. That is the right floor for "universal", because labs already produce reports in this shape.

**Record 1, chip identity.** ESCC 25100 requires the manufacturer, sample and control serial numbers, date code and mask set, technology (bulk CMOS, SOI, and so on) with feature size, die size, and the depth of the active region ([ESCC 25100](https://escies.org/escc-specs/published/25100.pdf)). Add the level tested (die, package, module or board), the memory type, and whether ECC is on. The level matters because modern accelerators are tested as modules, and the peripherals often fail first. On the Jetson Orin AGX module, the **MPQ86960 power regulators failed at 6 krad(Si)** under 150 MeV protons, long before the SoC did ([AFRL REACT, Orin AGX](https://exa.ai/library/publication/k9jg4jz8r66)).

**Record 2, total ionizing dose (TID) test.** Capture the source (Co-60, protons with their energy, or X-ray), the dose rate, the bias and its tolerance, the temperature, the dose steps, the parameters measured at each step, the failure dose and failure mode, and the anneal schedule. These fields are mandatory because results move with them. ESCC 22900 defines a standard window of **0.36–180 krad(Si)/h** and a low-rate window of **36–360 rad(Si)/h**. It requires worst-case bias held within 10%, and annealing at room temperature followed by a **168 h, 100 °C** bake ([ESCC 22900](https://escies.org/escc-specs/published/22900.pdf)). MIL-STD-883 TM 1019 adds its own condition letters, plus low-dose-rate and cryogenic conditions ([NEPP TM 1019 review](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/1140%20-%20Turflinger%20-%20NEPP%202019%20TM1019%20Rewrite%20Final.pdf)). The Orin AGX shows why the **beam energy and the test software must be recorded fields, not footnotes**. Co-60 gave a 42 krad(Si) threshold. A 150 MeV proton run failed at 6 krad(Si). A 64 MeV proton run at a different facility did not reproduce the early failure, and the authors attribute the gap to beam energy and test software ([AFRL REACT, Orin AGX](https://exa.ai/library/publication/k9jg4jz8r66)).

**Record 3, single-event effects (SEE) test.** A single event is one particle strike causing an upset, a hang or a latch-up. ESCC 25100 asks for a table with one row per run, giving the date and time, ion species and charge state, energy, LET (linear energy transfer, the energy a particle deposits per unit path), tilt angle and effective LET, device temperature, electrical conditions, flux, fluence, and the number and type of events (SEU, SEFI, SET, SEL, SEB, SEGR). It also asks for cross-section versus LET or energy, with error bars and a confidence level ([ESCC 25100](https://escies.org/escc-specs/published/25100.pdf)). The cross-section is events ÷ fluence, and tilted runs are corrected by cos θ ([ESCC 25100](https://escies.org/escc-specs/published/25100.pdf)). Turning a beam result into an on-orbit rate takes three more fields. CREME96's HUP module needs **Weibull parameters (saturation cross-section A, threshold, width W, shape s), the per-bit sensitive-volume dimensions x, y and z in µm, and the number of bits**. Treating a whole device as one sensitive volume grossly overestimates the rate ([CREME96 HUP](https://creme.isde.vanderbilt.edu/CREME-MC/help/hup-direct-ionization-induced-see-rate-calculation); [RPP method](https://creme.isde.vanderbilt.edu/CREME-MC/help/rpp-method)). For AI chips, add the **workload, power mode, and the silent-data-corruption (SDC) count**. In Google's TPU proton test, SDC appeared at roughly one event per 17 rad during transformer work. HBM uncorrectable errors came about every 44 rad (≈3×10⁻⁹ cm²/chip). Correctable-error counts were unavailable because firmware hid them below a vendor threshold ([Suncatcher preprint](https://arxiv.org/html/2511.19468v2)). The schema should therefore allow an explicit "not observable" value rather than a zero.

**Record 4, thermal and electrical wear test.** Wear in orbit isn't only radiation. JEDEC JEP122 gives Arrhenius acceleration, AF = exp[(−Eₐ/k)(1/T₁ − 1/T₂)], with activation energies that depend on the failure mechanism ([JEP122](https://www.jedec.org/sites/default/files/docs/JEP122H.pdf)). Electromigration follows Black's model in current density and temperature, whose parameters JESD63 estimates ([JESD63](https://www.jedec.org/standards-documents/docs/jesd-63)). Thermal cycling follows modified Coffin-Manson in cycle frequency, ΔT and T_max, with ΔT exponent β ≈ 2 ([NIST handbook](https://www.itl.nist.gov/div898/handbook/apr/section1/apr153.htm)). The record needs junction temperature, power, voltage, current density where known, the cycle profile (ΔT, T_max, frequency), the time or cycles to failure, the failure mechanism, and the activation energy used. In orbit, eclipse entries and exits are thermal cycles, so this record ties chip wear directly to position.

## Position-side records describe the place, then the radiation in it

**Record 5, vehicle trajectory.** Use CCSDS Orbit Data Messages (502.0-B-3) so any operator's file drops in. An OEM ephemeris requires `OBJECT_NAME`, `OBJECT_ID`, `CENTER_NAME`, `REF_FRAME`, `TIME_SYSTEM`, `START_TIME` and `STOP_TIME`, followed by state vectors and an optional covariance ([CCSDS 502.0-B-3](https://ccsds.org/Pubs/502x0b3e1.pdf); [Orekit OEM writer](https://test.orekit.org/site-orekit-13.0/jacoco/org.orekit.files.ccsds.ndm.odm.oem/OemWriter.java.html)). Time systems and frames come from a fixed list (UTC, TAI, GPS…; EME2000, GCRF, ITRF…), and anything else needs an ICD ([CCSDS 502.0-B-3](https://ccsds.org/Pubs/502x0b3e1.pdf)). Candidate positions the algorithm will rank can be supplied more compactly as mean elements (OMM): altitude, inclination, eccentricity, RAAN or local time of the ascending node, epoch and mission duration. The algorithm then derives beta angle and eclipse fraction itself.

**Record 6, environment along the trajectory.** IRENE (AE9/AP9/SPM) takes an ephemeris or orbital elements and returns flux, fluence, dose rate and accumulated dose. It offers mean, percentile (1–99), perturbed, and Monte-Carlo runs, and **meaningful percentiles need at least ten Monte-Carlo scenarios aggregated** ([IRENE user guide](https://www.vdl.afrl.af.mil/programs/ae9ap9/files/package/IRENE_Users_Guide.pdf)). The model is climatological: it covers a solar cycle statistically and does not predict a given phase ([IRENE factsheet](https://www.vdl.afrl.af.mil/programs/ae9ap9/factsheet.php)). For heavy ions, CREME96 chains geomagnetic shielding, flux, transport through shielding, LET spectrum, and rate. It distinguishes solar minimum, solar maximum, worst week and worst day ([How to run CREME96](https://creme.isde.vanderbilt.edu/CREME-MC/help/how-to-run-creme96); [BYU on-orbit SEU rates](https://scholarsarchive.byu.edu/cgi/viewcontent.cgi?article=1369&context=facpub)). Store the model and version, the run mode and percentile, the energy grid, the shielding assumed, and the output units. Never store a bare "dose" value.

**Record 7, placement inside the vehicle.** This record answers the second meaning of "position". The design system's `PlacementMap` already draws chips on a grid (`col`, `row`, `heat`), and its heat ramp is labelled from long life to short life. Each placement needs a location (grid cell or x, y, z), the shielding in front of it (material, density and thickness, or a sector-shielding distribution, which CREME96 can import) ([NASA CREME96 overview](https://ntrs.nasa.gov/api/citations/20120016823/downloads/20120016823.pdf)), and its local thermal coupling (radiator path, expected junction temperature range). Placement turns one orbit environment into a different dose and temperature for each chip.

## Outcome records are what make the algorithm improvable

**Record 8, observed outcomes.** These are the labels the evaluator scores against. On the ground, the best public baseline for NVIDIA data-center GPUs is Meta's Llama 3 run: **16,384 H100s over 54 days had 419 unexpected interruptions; 148 (30.1%) were faulty GPUs and 72 (17.2%) were HBM3** ([Llama 3 paper via ResearchGate](https://www.researchgate.net/publication/382739128_The_Llama_3_Herd_of_Models); [DCD](https://www.datacenterdynamics.com/en/news/meta-report-details-hundreds-of-gpu-and-hbm3-related-interruptions-to-llama-3-training-run/)). That gives a terrestrial failure floor before radiation adds anything. In orbit, each record needs the time window, the position (from record 5), the measured dose if a dosimeter flew, counts of upsets, resets and uncorrectable ECC errors, temperature telemetry, and the time to failure or censoring. "Censoring" means the chip was still alive when observation stopped, and it must be marked; otherwise survivors look like failures with unknown timing.

**Record 9, provenance (attached to every record).** Each value carries its source URL or DOI, the standard followed, the facility, the date, its units, and a confidence interval where one exists. It also carries a `value_status` of `measured`, `derived` or `assumed`. This reuses the `Sourced<T>` idea already in the 3rok codebase, so Grok can't silently turn an assumption into a fact. Public test reports to ingest are indexed in **NASA GSFC's radiation database** ([GSFC Rad Database](https://nepp.nasa.gov/radhome/RadDatabase/RadDataBase.html)) and **ESA's radiation test database** ([esarad.esa.int](https://esarad.esa.int/)).

| # | Record | Minimum required fields | Standard / contract |
|---|---|---|---|
| 1 | Chip identity | part number, family, node, die area, level tested, memory/ECC, serials, date code | ESCC 25100 |
| 2 | TID test | source + energy, dose rate, bias, temp, dose steps, failure dose + mode, anneal | ESCC 22900, TM 1019 |
| 3 | SEE test | particle, energy, LET/eff. LET, tilt, flux, fluence, events by type, σ with CI, power mode, workload, SDC; Weibull + RPP + bits if available | ESCC 25100, JESD57/JESD234, CREME96 HUP |
| 4 | Thermal/electrical wear | Tj, power, V, J, ΔT/Tmax/freq, time-to-fail, mechanism, Eₐ | JEP122, JESD63 |
| 5 | Trajectory | OEM header + states, or OMM elements; epoch; duration | CCSDS 502.0-B-3 |
| 6 | Environment | model + version, mode, percentile, energies, shielding, flux/fluence/dose with units | IRENE AE9/AP9, CREME96 |
| 7 | Placement | location, shielding (material, thickness or sector), thermal coupling | CREME96 shielding input |
| 8 | Outcome | window, position ref, dose, upsets/resets/UECC, temps, failure or censor time | field logs, telemetry |
| 9 | Provenance | source, standard, facility, date, units, CI, value_status, split | applies to all |

## Public NVIDIA data fills the demo, with one hole

For the demo, the Jetson Orin family has proper beam data. The **Orin NX** was tested with 480 MeV protons at TRIUMF. Its SoC SEU cross-section is about 3.9×10⁻⁹ cm² at 15 W, from a fluence of 5.65×10⁹ p/cm². At subsystem level, the GPU's SEFI cross-section of 6.5×10⁻¹⁰ cm² was larger than its SEU cross-section of 3.5×10⁻¹⁰ cm², meaning GPU strikes mostly halted execution rather than being corrected. The paper reports lower and upper bounds throughout ([Orin NX SEE, UPC](https://upcommons.upc.edu/bitstreams/ef814395-1619-43ee-ba00-6a89f0c16d83/download)). The same Orin NX modules survived **past 36.2 krad(Si)** of TID ([Orin NX TID](https://www.researchgate.net/publication/387116286_Total_Ionizing_Dose_Radiation_Testing_of_NVIDIA_Jetson_Orin_NX_System_on_Module)). The **Orin AGX** was first reported as limited to 19 krad(Si) ([IEEE REDW 2023](https://ieeexplore.ieee.org/document/10265818)). Later work refined that to 42 krad(Si) under Co-60, alongside the 6 krad(Si) proton regulator failure described above ([AFRL REACT](https://exa.ai/library/publication/k9jg4jz8r66)). Together these fill records 1–3 for an NVIDIA chip and already show the spread across facilities that the algorithm has to tolerate. Meta's H100 interruptions fill record 8 for the ground. Google's TPU results are a useful non-NVIDIA cross-check: no hard TID failure up to 15 krad(Si), and a shielded dawn-dusk orbit estimated at about 150 rad(Si)/year ([Suncatcher preprint](https://arxiv.org/html/2511.19468v2)).

The hole is the chip the pitch is actually about. In this pass I found **no public proton or heavy-ion data for the H100 or newer data-center GPUs**, and no public telemetry from the H100 flying on Starcloud-1. The demo can show that the pipeline accepts data-center GPU records, but its predictions should be labelled as built on Jetson-class data. Orin is a 7 nm automotive SoC on a module with LPDDR5 ([Orin NX SEE, UPC](https://upcommons.upc.edu/bitstreams/ef814395-1619-43ee-ba00-6a89f0c16d83/download)); an H100 with HBM3 at 700 W is a different device.

## Conclusion

The guidelines turn "train AI on chip data" into a data contract, and that contract changes the product question. A model that only retrieves can't learn wear. It can propose better formulas, and a held-out evaluator can prove whether they are better. The scarce input is therefore not chip test data, which exists in standard form, but **outcome data tied to a known position**. Without it, every "optimal position" is untested.

This sits in tension with the Project's earlier product vision, which argued that an optimal coordinate is not well defined. The tension is resolvable if three rules hold. The algorithm ranks regions of candidate orbits and placements rather than naming a single point. Every output carries the IRENE percentile and test confidence interval it came from. And Grok's edits are accepted only when the held-out score improves. The coordinator should decide whether the demo adopts that framing.
